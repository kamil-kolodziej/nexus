## Requirement Completeness

- [x] CHK001 - Are text preprocessing requirements specified for non-ASCII characters, HTML entities, or Unicode edge cases in article text? [Gap] **Out of scope for v1**: VADER and FinBERT accept arbitrary Unicode. HTML entity handling is upstream (nexus-ingestion). No preprocessing needed.
- [x] CHK002 - Is the consumer group auto-creation behavior fully specified — what happens if `nexus:news-events` stream does not exist at startup? [Completeness, Spec §FR-001] **RESOLVED**: FR-001 updated to specify `XGROUP CREATE ... $ MKSTREAM` with `BUSYGROUP` error handling.
- [x] CHK003 - Are graceful shutdown requirements defined for the consumer loop (e.g., finish current message vs. immediate stop on SIGTERM/SIGINT)? [Gap] **RESOLVED**: Added edge case specifying stop flag, finish in-flight message, flush writer, then exit.
- [x] CHK004 - Are startup ordering requirements documented — must Redis and TimescaleDB be reachable before the consumer loop starts? [Gap] **RESOLVED**: Added edge case — Redis required (exit on failure), TimescaleDB best-effort (start without, retry in background).
- [x] CHK005 - Is the TimescaleDB persistence failure path fully specified — what happens when the async writer queue is full? [Completeness, Spec §FR-013] **OK**: FR-013 says "same pattern as nexus-ingestion TimescaleDB writer" which drops events on full queue with a warning log. Pattern is documented in research §8 and existing code.
- [x] CHK006 - Are logging requirements specified for normal operation (what structured events are emitted per article processed, per fan-out publish)? [Gap] **OK**: Spec delegates to structlog conventions in CLAUDE.md. Implementation detail — log events will follow snake_case convention per project standards.
- [x] CHK007 - Is the VADER confidence derivation (`abs(compound)`) documented in the spec or only in assumptions? [Completeness, Spec §Assumptions] **OK**: Documented in Assumptions section and research §1. Assumptions are normative per speckit convention.
- [x] CHK008 - Are requirements defined for the `pending_claim_threshold` sweep interval — how often does the claim sweep run? [Gap, Spec §FR-015] **RESOLVED**: FR-015 updated to specify configurable `claim_sweep_interval` (default 60 seconds) and `XAUTOCLAIM`.
- [x] CHK009 - Is the consumer name format for `XREADGROUP` (e.g., `consumer-{hostname}`) specified in requirements or only in research? [Completeness, Spec §FR-001] **OK**: Implementation detail. Research §4 documents it; spec correctly stays at requirements level (consumer group name).
- [x] CHK010 - Are requirements specified for what happens when the asset dictionary YAML file is missing or malformed at startup? [Gap, Spec §FR-017] **RESOLVED**: FR-017 updated — missing or malformed dictionary causes immediate exit (non-recoverable, same as model load failure).
- [x] CHK011 - Is the `active_assets` configuration field documented in the spec's requirements section, or only in plan/data-model artifacts? [Completeness, Spec §FR-019] **RESOLVED**: FR-019 updated to explicitly reference `active_assets` config list with env var and TOML paths.
- [x] CHK012 - Are Docker Compose service definitions and container configuration requirements documented for `nexus-sentiment`? [Gap] **Out of scope for v1**: Docker Compose config is an ops artifact, not a requirements concern. Will be created during implementation alongside Dockerfile.

## Requirement Clarity

- [x] CHK013 - Is the text combination formula `headline + ". " + body_summary` unambiguous when `body_summary` is empty? Does it produce `"headline. "` or `"headline"`? [Clarity, Spec §FR-002] **RESOLVED**: FR-002 updated — just `headline` when `body_summary` is empty (no trailing period).
- [x] CHK014 - Is "within 1 second" (SC-001) measured from XADD timestamp of the NewsArticle to XADD timestamp of the SentimentScore, or from XREADGROUP receipt to publish? [Clarity, Spec §SC-001] **OK**: SC-001 says "appearing in nexus:news-events" to "appears in nexus:sentiment-events" — this is wall-clock end-to-end (XADD to XADD). Sufficiently clear for an integration test.
- [x] CHK015 - Is "currently configured or tradable in Nexus" (FR-019) precisely defined — does this mean the `active_assets` config list, exchange-reported tradable pairs, or both? [Ambiguity, Spec §FR-019] **RESOLVED**: FR-019 now explicitly says `active_assets` configuration list.
- [x] CHK016 - Is the `model_id` format `"{processor}:{version}"` precisely defined — is it the library version (e.g., `vaderSentiment.__version__`) or a custom version string? [Clarity, Spec §SentimentScore entity] **OK**: Research §1 and §2 explicitly define `"vader:{vaderSentiment.__version__}"` and `"finbert:{transformers.__version__}"`. Spec entity says "identifier of the NLP model" — implementation detail appropriately in research.
- [x] CHK017 - Is the term "acknowledged and dropped" (FR-014) clear on sequencing — is XACK called before or after the warning log? [Clarity, Spec §FR-014] **OK**: Sequencing is an implementation detail. "Logged as a warning" and "acknowledged" are both required; the order doesn't change observable behavior.
- [x] CHK018 - Is "the same inference run" (User Story 2, scenario 3) defined — does it mean a single `analyze()` call whose result is reused, or independent calls that happen to produce the same output? [Ambiguity, Spec §US-2] **RESOLVED**: US-2 scenario 3 updated to explicitly state "single `analyze()` call, result reused for fan-out."
- [x] CHK019 - Is the FinBERT truncation behavior specified — what happens when combined text exceeds 512 tokens? Is it silently truncated or logged? [Clarity, Spec §FR-007] **OK**: Research §2 documents `truncation=True` at tokenization. Most inputs fit within limits (body_summary capped at 1000 chars). Silent truncation is standard transformers behavior — not a spec concern.
- [x] CHK020 - Is the `score=0.0, confidence=0.0` zero-signal for empty text (Edge Case 1) distinguishable from a genuine neutral score with low confidence? [Clarity, Spec §Edge Cases] **OK**: `confidence=0.0` is impossible for non-empty text (VADER: `abs(compound)` > 0 for any text; FinBERT: `max(probs)` ≥ 0.33). The zero-signal is distinguishable by `confidence=0.0` exactly.

## Acceptance Criteria Quality

- [x] CHK028 - Can SC-001 latency targets (≤1s VADER, ≤2s FinBERT) be objectively measured in an automated test without timing flakiness? [Measurability, Spec §SC-001] **OK**: Measurable via integration test with generous margins (e.g., 5s timeout). Exact timing is flaky in CI; test should verify "within order of magnitude" and use a manual benchmark for precise validation.
- [x] CHK029 - Can SC-005 score/confidence range invariants be verified with property-based tests as stated, or do they also need boundary value tests (exactly -1.0, +1.0, 0.0, 1.0)? [Measurability, Spec §SC-005] **OK**: Property-based tests (Hypothesis) inherently cover boundaries via shrinking. Explicit boundary tests are good practice but not a spec gap — implementation will include both.
- [x] CHK030 - Is SC-006 (no credentials/weights/paths in output) testable via automated assertion, or does it require manual review? [Measurability, Spec §SC-006] **OK**: Testable via automated regex/pattern assertions on serialized event payloads, log output, and health alert messages. SRC-003 constrains model_id format.
- [x] CHK031 - Can SC-003 (service continues after inference error, pending count doesn't grow unboundedly) be tested deterministically, or is "unboundedly" vague? [Measurability, Spec §SC-003] **OK**: "Unboundedly" means the dead-letter claim sweep (FR-015) eventually acknowledges stale pending messages. Test: inject N errors, verify claim sweep runs and pending count decreases. Deterministic.
- [x] CHK032 - Are acceptance scenarios for User Story 3 (asset extraction) testable without access to the specific dictionary content — are test dictionary entries specified? [Measurability, Spec §US-3] **OK**: Tests will use a test-specific dictionary fixture (implementation detail). The scenarios use universal examples ("Bitcoin" → BTC/USDT) that any reasonable dictionary would contain.

## Scenario Coverage

- [x] CHK033 - Are requirements defined for concurrent message processing scenarios — can the consumer process multiple messages simultaneously, or is it strictly sequential? [Coverage, Gap] **RESOLVED**: FR-001 updated to specify "messages are processed sequentially (one at a time per consumer instance)."
- [x] CHK034 - Are requirements specified for service behavior during Redis Stream trimming — what if older unprocessed messages are trimmed before the consumer reads them? [Coverage, Gap] **OK**: Consumer group tracking (`>` read) prevents this — XREADGROUP delivers only messages not yet delivered to this consumer. Trimming only affects messages already consumed. Redis Streams guarantee this by design.
- [x] CHK035 - Are requirements defined for the case where `nexus:sentiment-events` stream reaches MAXLEN — is approximate trimming applied to outputs? [Coverage, Spec §contracts vs FR-003] **OK**: Contracts doc specifies `MAXLEN ~50,000` with approximate trimming. Plan and research §4 confirm. Implementation detail — not a spec gap.
- [x] CHK036 - Are requirements specified for multiple instances of `nexus-sentiment` running concurrently in the same consumer group (horizontal scaling)? [Coverage, Gap] **Out of scope for v1**: Single instance is sufficient for ≤100 articles/minute. Consumer group semantics naturally support horizontal scaling. Will document when scaling is needed.
- [x] CHK037 - Are requirements specified for the transition from VADER to FinBERT (or vice versa) — can historical scores from different models coexist in the output stream? [Coverage, Gap] **OK**: `model_id` field in SentimentScore identifies the processor. Scores from different models coexist naturally. SRC-005 requires restart for model change. No conflict.
- [x] CHK038 - Are requirements defined for handling `related_assets` entries that use the `sector:` prefix but don't match any known sector in the dictionary? [Coverage, Spec §FR-016 vs §FR-019] **Out of scope for v1**: `related_assets` entries bypass the dictionary — they go directly to the active-universe filter (FR-019). If `sector:foo` is in `active_assets`, it's used. If not, it's filtered out. This is correct behavior; no additional spec needed.
- [x] CHK039 - Are requirements specified for the case where the extraction dictionary is updated (file changed) while the service is running? [Coverage, Spec §FR-017] **RESOLVED**: FR-017 updated — "NOT reloaded at runtime; changes require a service restart."

## Edge Case Coverage

- [x] CHK040 - Is the behavior specified when `related_assets` contains entries that are not valid ccxt symbols or `sector:` tags (e.g., arbitrary strings like `"foo"`)? [Edge Case, Gap] **RESOLVED**: Added edge case — entries not in `active_assets` are silently filtered out by FR-019.
- [x] CHK041 - Is the behavior specified when `body_summary` contains the maximum 1000 characters of highly repetitive or adversarial text? [Edge Case, Gap] **Out of scope for v1**: VADER and FinBERT handle arbitrary text without crashing. Adversarial inputs may produce low-quality scores but won't cause failures. Security review can address prompt-injection-style attacks later.
- [x] CHK042 - Is the behavior specified when the same article URL appears in multiple consecutive NewsArticle events (upstream dedup failure)? [Edge Case, Gap] **Out of scope for v1**: At-least-once semantics already specify duplicate handling (edge case: "same article redelivered"). Upstream dedup is nexus-ingestion's responsibility. Duplicate scores are acceptable.
- [x] CHK043 - Is the behavior specified for articles in non-English languages — does VADER/FinBERT handle or reject them? [Edge Case, Gap] **Out of scope for v1**: VADER is English-only (produces near-zero compound for non-English). FinBERT is English-only (PhraseBank trained on English). Non-English articles produce low-confidence/neutral scores — degraded but not incorrect. Language detection is a future enhancement.
- [x] CHK044 - Is the behavior specified when a FinBERT inference returns equal probabilities for all three classes (perfect three-way tie)? [Edge Case, Spec §Assumptions] **Out of scope for v1**: A perfect 0.333/0.333/0.333 tie produces `score = 0.0`, `confidence = 0.333`, `label = neutral` (or whichever class is first in argmax — tie-breaking is library-defined). Valid output, not an error condition.
- [x] CHK045 - Is the behavior specified when `related_assets` contains an extremely large number of entries (e.g., 100+)? Is fan-out bounded? [Edge Case, Gap] **RESOLVED**: Added edge case — fan-out bounded by configurable `max_fan_out` (default 50). Excess entries dropped with warning log.
- [x] CHK046 - Is the behavior specified when the extraction dictionary contains overlapping aliases (e.g., "Ethereum" maps to both `ETH/USDT` and `ETH/BTC`)? [Edge Case, Spec §FR-017] **Out of scope for v1**: The dictionary is curated (FR-020). Overlapping aliases are a dictionary authoring error. If present, both matches are included in the effective asset list (both pass word-boundary matching). Dictionary validation is a future improvement.
- [x] CHK047 - Is the behavior specified when the Redis connection drops during the `XACK` call (after all publishes succeed but before acknowledgment)? [Edge Case, Gap] **RESOLVED**: Added edge case — message remains pending, reprocessed on restart or claimed by sweep. Duplicate scores expected under at-least-once semantics.

## Non-Functional Requirements

- [x] CHK048 - Are memory usage requirements or limits specified for FinBERT model loading (~440MB)? [Non-Functional, Gap] **Out of scope for v1**: ~440MB is documented in assumptions. Memory limits are an ops concern (Docker memory limits). Not a spec requirement.
- [x] CHK049 - Are resource cleanup requirements specified for the thread pool executor on service shutdown? [Non-Functional, Gap] **Out of scope for v1**: Default asyncio thread pool is cleaned up by the event loop on shutdown. Custom cleanup not needed.
- [x] CHK050 - Are log volume requirements specified — at high article throughput, could per-article logging create excessive log output? [Non-Functional, Gap] **Out of scope for v1**: At ≤100 articles/minute, per-article logging is ~100 lines/minute. Not excessive. Throttle if scale increases.
- [x] CHK051 - Is the health endpoint's 200ms response time requirement (FR-010) specified under load conditions, or only for idle state? [Non-Functional, Spec §FR-010] **OK**: Health endpoint reads in-memory counters only (no I/O). Response time is <1ms regardless of load. The 200ms target is a safety margin, not a stretch goal.
- [x] CHK052 - Are backpressure requirements defined — what happens if articles arrive faster than inference can process them? [Non-Functional, Gap] **Out of scope for v1**: Redis consumer group naturally provides backpressure — unread messages accumulate in the stream (bounded by MAXLEN). Sequential processing (FR-001) means the consumer processes at its own pace. No data loss.
- [x] CHK053 - Are observability requirements beyond health endpoint specified (e.g., metrics, tracing, structured log correlation IDs)? [Non-Functional, Gap] **Out of scope for v1**: Structlog events provide structured observability. Prometheus metrics and tracing are future enhancements.
